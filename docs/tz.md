## 2 Назначение и цели создания системы

### 2.1 Назначение системы

Система предназначена для централизованного управления доступом сотрудников к сетевым ресурсам организации: автоматизации выдачи, изменения и отзыва прав доступа, ведения единого каталога сетевых ресурсов и журнала аудита всех операций с правами доступа.

### 2.2 Цели создания системы

Целями создания системы являются:

1. автоматизация процессов выдачи и отзыва прав доступа к сетевым ресурсам ООО «АСЛАНАРТ»;
2. создание единого каталога сетевых ресурсов организации;
3. обеспечение разграничения доступа к сетевым ресурсам на основе атрибутов субъектов и объектов (модель ABAC);
4. обеспечение прозрачности и контролируемости операций с правами доступа посредством журнала аудита;
5. снижение трудозатрат ИТ-персонала на выдачу и контроль доступа;
6. повышение уровня защищённости информации, обрабатываемой в информационной системе организации.

### 2.3 Критерии оценки достижения целей

Достижение целей подтверждается:

- функционированием всех функций системы, предусмотренных разделом 4;
- прохождением испытаний по программе и методике испытаний (ГОСТ 19.301-79);
- результатами тестирования безопасности (отсутствие критических уязвимостей по ГОСТ Р 71207-2024);
- актом о внедрении в деятельность ООО «АСЛАНАРТ».

## 3 Характеристика объекта автоматизации

### 3.1 Общие сведения об объекте

Объектом автоматизации является процесс управления доступом сотрудников ООО «АСЛАНАРТ» (г. Санкт-Петербург) к сетевым ресурсам организации. Численность сотрудников — 30 человек. ИТ-инфраструктура эксплуатируется силами штатного администратора.

### 3.2 Сетевые ресурсы организации

Объектами учёта системы являются следующие классы сетевых ресурсов:

| Класс ресурса | Примеры | Действия (права) |
|---|---|---|
| Файловые хранилища | SMB-шары, сетевые папки | read / write / manage |
| СУБД | базы данных учёта | connect / select / modify |
| Сетевые печатные устройства | принтеры отделов | print / manage |
| Внутренние веб-сервисы | CRM, учётные сервисы | access / admin |
| Серверы и VPN | SSH-доступ, туннели | connect / admin |

Перечень конкретных ресурсов уточняется при внедрении по данным заказчика.

### 3.3 Текущий процесс управления доступом

В настоящее время выдача и отзыв прав доступа выполняются администратором вручную по устной или письменной заявке сотрудника или руководителя. Выявлены следующие недостатки:

- отсутствие единого каталога сетевых ресурсов;
- разрозненное, частично несистематизированное назначение прав;
- отсутствие централизованного журнала аудита изменений прав;
- невозможность оперативно определить, кто и к каким ресурсам имеет доступ;
- риск несанкционированного сохранения прав после увольнения или смены должности.

## 4 Требования к системе

### 4.1 Требования к системе в целом

#### 4.1.1 Требования к структуре и составу

1. Система должна иметь клиент-серверную архитектуру и состоять из:
   - серверного приложения (Qt Network, TCP), выполняющего хранение данных, бизнес-логику и проверку прав доступа;
   - клиентского приложения (Qt Quick / QML) для работы пользователей и администратора;
   - реляционной базы данных PostgreSQL как хранилища.
2. Клиент и сервер должны взаимодействовать по разработанному протоколу поверх TCP (раздел 2.3 ВКР, документ «Протокол взаимодействия»).
3. Система должна быть кроссплатформенной: сервер и клиент должны собираться и работать на ОС Windows и Linux; клиент дополнительно — на macOS.

#### 4.1.2 Требования к численности и квалификации персонала

Для работы с системой требуется персонал:

- администратор (1–2 чел.) — настройка системы, управление каталогом ресурсов, политиками доступа и пользователями;
- пользователи (до 30 чел.) — просмотр доступных ресурсов, подача заявок (при необходимости), работа с выданными правами;
- аудитор (опционально) — просмотр журнала аудита без права изменения.

#### 4.1.3 Показатели назначения

1. Количество обслуживаемых пользователей — до 100.
2. Количество учитываемых ресурсов — до 1000.
3. Время отклика сервера на запрос проверки доступа — не более 100 мс в штатном режиме.
4. Время запуска сервера — не более 10 с.
5. Система должна поддерживать одновременные сессии не менее 20 клиентов.

#### 4.1.4 Требования к надёжности

1. Сервер должен быть отказоустойчивым к одиночным сбоям: повторная попытка подключения клиента, восстановление соединения.
2. Отказ клиента не должен нарушать работу сервера.
3. Обработка ошибочных и некорректных запросов не должна приводить к аварийному завершению сервера.
4. Данные в PostgreSQL должны быть защищены транзакциями и ограничениями целостности.
5. Среднее время восстановления после сбоя — не более 30 минут (перезапуск сервера и восстановление соединения с БД).

#### 4.1.5 Требования к безопасности (защите информации)

Система обрабатывает персональные данные сотрудников и является информационной системой персональных данных (ИСПДн).

1. Класс ИСПДн: категория обрабатываемых персональных данных — 4 («иные»), количество субъектов — менее 100 000, актуальные угрозы 3-го типа. Требуемый уровень защищённости — **УЗ-3** (ПП РФ № 1119 от 01.11.2012).
2. Реализовать идентификацию и аутентификацию пользователей (ИАФ.1, ИАФ.2, ИАФ.3, ИАФ.4):
   - учётные записи и пароли; политика паролей (длина не менее 8 символов, смена не реже чем раз в 180 дней, запрет простых паролей);
   - блокировка учётной записи после 5 неудачных попыток аутентификации на 15 минут;
   - деактивация неиспользуемых учётных записей (30 дней без входа);
   - хранение паролей в виде хешей (PBKDF2 / Argon2), исключение хранения в открытом виде.
3. Реализовать управление доступом (УПД.1–УПД.5) на основе модели ABAC:
   - проверка прав на каждый запрос к серверу и каждую операцию с ресурсом;
   - атрибуты субъекта: идентификатор, роль (как атрибут), уровень допуска (clearance level), множество разрешённых действий;
   - атрибуты объекта: тип ресурса, требуемые действия (required permissions);
   - централизованное описание политик доступа и их управление администратором.
4. Реализовать аудит безопасности (АУД.1, АУД.2, АУД.3) в соответствии с ГОСТ Р 59548-2022:
   - регистрация событий: вход/выход, успешные и неудачные попытки доступа, изменения прав, управление ресурсами и пользователями, изменение политик;
   - хранение журнала с защитой от модификации; журнал доступен только аудитору и администратору;
   - невозможность изменения или удаления записей журнала штатными средствами клиента.
5. Обеспечить защиту информации при передаче (ЗИС.2): шифрование канала между клиентом и сервером (TLS).
6. Защитить данные на уровне СУБД: сервисная учётная запись с минимально необходимыми привилегиями (не суперпользователь), параметризованные SQL-запросы (prepared statements) для исключения SQL-инъекций.
7. Реализовать контроль целостности: проверка конфигурации, версионирование, обновление (ОИА.1–ОИА.3).
8. Обеспечить возможность реагирования на инциденты (СРС.2): сигнальные сообщения в журнал при множественных неудачных попытках, блокировка.
9. Провести статический анализ кода (SAST) по ГОСТ Р 71207-2024 и устранить выявленные уязвимости (ГОСТ Р 56545-2015).
10. Ввести практики безопасной разработки по ГОСТ Р 56939-2024 (обучение, управление требованиями безопасности, контроль зависимостей, тестирование безопасности).

#### 4.1.6 Требования к эргономике и удобству использования

1. Интерфейс клиента должен быть интуитивно понятным для пользователя без специальной подготовки.
2. Все операции по выдаче и отзыву прав должны выполняться не более чем в 3–4 клика.
3. Интерфейс должен поддерживать **два языка: русский и английский** (переключатель языка; локализация посредством Qt Linguist, `.ts`/`.qm`).

#### 4.1.7 Требования к эксплуатации, техническому обслуживанию, ремонту и хранению

1. Система должна эксплуатироваться в круглосуточном режиме (24×7) на сервере организации под управлением ОС Linux (рекомендуется) или Windows.
2. Административные операции (настройка, резервное копирование БД) не должны требовать остановки сервера.
3. Резервное копирование БД — штатными средствами PostgreSQL (pg_dump); периодичность — ежесуточно.

#### 4.1.8 Требования к защите информации от несанкционированного доступа

Разграничение доступа к функциям системы по ролям (атрибутам):

- **Администратор** — управление пользователями, ресурсами, политиками; просмотр журнала;
- **Пользователь** — просмотр доступных ему ресурсов, доступ в соответствии с выданными правами;
- **Аудитор** — просмотр журнала аудита (read-only);
- доступ к функциям проверяется на сервере при каждом запросе.

#### 4.1.9 Требования по сохранности информации при авариях

1. Восстановление БД из резервной копии — не более 1 часа.
2. Повреждение файла конфигурации сервера не должно приводить к потере данных (перезапуск с резервной конфигурацией).

#### 4.1.10 Требования к патентной чистоте

1. Реализация не должна нарушать патенты третьих лиц.
2. Используемые компоненты имеют свободные лицензии: Qt (LGPL/GPL), PostgreSQL (PostgreSQL License), прочие зависимости — по `conanfile.py`.

#### 4.1.11 Требования к стандартизации и унификации

1. Использовать единый стиль кодирования (`.clang-format`, clang-tidy).
2. Код на C++20, сборка CMake (≥ 3.31), менеджер зависимостей Conan 2.
3. Документация оформляется в соответствии с ЕСПД (ГОСТ 19.xxx) и ЕСКД (ГОСТ 2.105-2019).

### 4.2 Требования к функциям (задачам), выполняемым системой

#### 4.2.1 Управление пользователями

1. Создание, редактирование, деактивация учётных записей.
2. Назначение ролей и атрибутов субъектов (включая уровень допуска, множество разрешённых действий).
3. Управление паролями (сброс, блокировка, разблокировка).

#### 4.2.2 Ведение каталога сетевых ресурсов

1. Добавление, редактирование, удаление записей о ресурсах всех классов (раздел 3.2).
2. Задание для каждого ресурса типа и требуемых действий (required permissions).
3. Каталогизация по классам и метаданным (наименование, описание, адрес).

#### 4.2.3 Управление политиками доступа (ABAC)

1. Формирование и изменение правил доступа: «субъект с атрибутом A получает действие P на ресурс типа T».
2. Проверка доступа: функция `evaluate_policy(subject, resource)` возвращает разрешение/отказ с обоснованием.
3. Правило по умолчанию — запрет (deny by default).

#### 4.2.4 Разграничение доступа на уровне протокола

1. Аутентификация клиента при установлении соединения.
2. Проверка прав на каждую операцию сервером (авторизация на сервере, не в клиенте).
3. Отказ в доступе возвращается клиенту в виде структурированного сообщения с кодом причины.

#### 4.2.5 Журнал аудита

1. Регистрация событий безопасности (раздел 4.1.5, п. 4).
2. Просмотр журнала с фильтрацией по времени, субъекту, объекту, типу события.
3. Экспорт журнала в файл (CSV) для анализа аудитором.

#### 4.2.6 Локализация

1. Поддержка русского и английского языков интерфейса.
2. Переключение языка без перезапуска приложения (или с перезапуском — по решению проектирования).

#### 4.2.7 Администрирование

1. Конфигурирование параметров подключения к БД и прослушиваемого порта через конфигурационный файл.
2. Просмотр состояния сервера (активные сессии, статистика).

### 4.3 Требования к видам обеспечения

#### 4.3.1 Математическое обеспечение

1. Модель управления доступом ABAC: субъект с атрибутами, объект с атрибутами, политики; функция принятия решения `evaluate_policy`.
2. Модель прав действий: read / write / manage / connect / select / modify / print / access / admin.
3. Семантика прав по умолчанию: отсутствие правила → запрет.

#### 4.3.2 Информационное обеспечение

1. СУБД PostgreSQL (поддерживаются версии 13–17).
2. Состав данных: пользователи, атрибуты субъектов, ресурсы, атрибуты объектов, политики доступа, журнал аудита.
3. Словарь данных и SQL-скрипты создания схемы — в составе рабочей документации (Приложение 3 ВКР).
4. Значения кодов операций и кодов отказов протокола — в документе «Протокол взаимодействия».

#### 4.3.3 Программное обеспечение

1. Язык C++20.
2. Фреймворк Qt 6.8 (модули Core, Gui, Qml, Quick, Network, Sql).
3. Драйвер QPSQL для PostgreSQL.
4. Инструменты: CMake ≥ 3.31, Conan 2, Ninja, clang-format, clang-tidy, clangd, санитайзеры (ASan/UBSan в Debug).
5. CI: GitHub Actions (Windows + MSVC/Qt, Ubuntu + GCC/Qt).

#### 4.3.4 Лингвистическое обеспечение

1. Языки интерфейса: русский, английский.
2. Использование Qt Linguist: `lupdate`/`lrelease`, файлы `.ts`/`.qm`.
3. Кодировка текстов — UTF-8.

#### 4.3.5 Техническое обеспечение

1. Сервер: x86-64, ОС Linux (Debian/Ubuntu) или Windows 10/11, RAM ≥ 4 ГБ, диск ≥ 20 ГБ (включая БД), статический IP.
2. Клиент: x86-64, ОС Linux/Windows/macOS, дисплей ≥ 1280×720.
3. Сетевое соединение: TCP/IP, канал не ниже 100 Мбит/с.

#### 4.3.6 Организационное обеспечение

1. Регламент назначения администратора и аудитора системы.
2. Инструкция по работе с системой (руководство пользователя).
3. Регламент резервного копирования и восстановления.

#### 4.3.7 Методическое обеспечение

1. Методика и критерии оценки эффективности внедрения (сокращение трудозатрат на выдачу доступа, прозрачность учёта).
2. Методика тестирования (программа и методика испытаний, ГОСТ 19.301-79).

## 7 Требования к составу и содержанию работ по подготовке объекта автоматизации к вводу системы в действие

4. Импорт/ввод начальных данных: каталог ресурсов, пользователи, политики.
5. Обучение администратора и пользователей.
6. Пробная эксплуатация в течение одной недели.
